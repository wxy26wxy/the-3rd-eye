## Findings

### Major
1. **Late `describe` after a quick second action overwrites the newer description.** `web/lib/pipeline/artworks.ts:617-625` (`adoptReadyCut`), `web/lib/db/queries.ts:200` (`updateArtwork`).
   What: the deferred describe reads the adopted cut, then calls `updateArtwork(id, {altText, spokenDescription, differencesFromPrompt})` with no condition. If the creator picks again, or makes a marks re-cut (which describes before answering), within the 3-4 s the first describe takes, the first describe lands last and the row carries the description of a picture it no longer shows.
   Why Major: the alt text and spoken description are what a blind creator hears for the sticker; a wrong one is a content error in the product's core accessibility output, and the window is the normal "tap, Use this, Fix the cutout" sequence. The fix is cheap.
   Fix: write only while the row still holds the cut the description was made from. Add a conditional write, for example `updateArtworkIfCut(id, cleanedUrl, patch)` in `queries.ts` doing `update artworks set ... where id = $1 and cleaned_url = $2 returning *` (or `updateArtwork` with an optional `where` guard), and call it with the `cleanedUrl` captured at line 617. A zero-row result is a silent no-op. This is also correct against a later marks re-cut, which writes a new `cleanedUrl`. Add a test: adopt, then change the row's `cleanedUrl`, then run the queued after-task; the description must not be written.
2. **`docs/api.md` does not say that a pick drops earlier marks on that piece.** `docs/api.md:288-296` (item 3 of "Cut once, tap locally"); also absent from `docs/handoffs/backend.md`. Only the ADR (`docs/decisions.md`, trade-offs) and the report mention it.
   Why: the clients read api.md, and they are being built to force a pick after marks. A pick adopts the candidate's raw cut, so the marks are silently lost, and the answer looks like success.
   Fix (docs, required): state in item 3 and in the handoff that a pick of a piece replaces the row's cut with that piece's original cut, so marks made on that piece before are not kept; the client must not send a pick after marks unless it wants them dropped. Optional hardening for the PM to decide (small, would remove the footgun): after a marks re-cut with exactly one `candidateIds` entry, store the new cut on that candidate with `setCandidateCut` (a later pick then adopts the marked cut, and the strip shows it). Not needed for the contract.

### Minor
3. `docs/api.md:290` says `candidates[0]`'s `cleanedUrl` "is set when the detection answers". True for `detect`, `framed`, `cutout` and the single auto-selected candidate, but on the plain photo path with the picker shown nothing is cut at answer time (`web/lib/pipeline/artworks.ts:248-249`), so candidate 0 is cut in the background like the rest. Say so.
4. `web/lib/pipeline/artworks.ts:248-249`: on the plain photo path the pieces are cut in `findCandidates` order, which is SAM score order (`web/lib/ai/meta/sam.ts:237`), not largest first. This is the strip order, so the visible pieces are still ready first; only the api.md/ADR wording "largest first" is loose for this path. Reword, or sort by `area` like `cutoutArtwork` does (line 525).
5. `web/lib/pipeline/artworks.ts:293-303`: a background cut for a candidate that was replaced meanwhile still does the whole cut and uploads two files before `setCandidateCut` turns out to be a no-op (orphaned blobs, wasted memory). Cheap mitigation: skip the remaining queue when `setCandidateCut` finds nothing (return a boolean from it, e.g. via `returning`), so a replaced detection stops its worker after at most the two pieces in flight.
6. Test gaps (`web/test/candidate-cuts-t155.test.ts`): the tests pin fields written, `cutParts`-free adopt, fallbacks, the inline and deferred `runAfterResponse` paths, and the SQL shape of `setCandidateCut`. They do not pin: cut order (largest first), the cap of 6, concurrency 2, the pipeline-level "replaced candidates are not resurrected" (the mock has the guard but no test drives it), or that `points` force a re-cut (the test named "marks, or a box smaller" only tries the small box). Add the points case and an order assertion (record `cutParts`/storage call order with three different sizes); the late-describe test from Major 1.
7. Memory: no unnecessary duplicate of the original is held (all workers share the one `png` buffer; `cutParts` makes an upscaled copy only when the cut is under the minimum size). Two concurrent cuts at 2048 px long side are fine (a few tens of MB raw RGBA each, up to about 4x when a small piece is upscaled x2). Note only: the plain photo path with an old client that does not cap at 2048 can hold a 25 MB-upload-sized picture, so up to about 50 MB raw per cut plus the 6 full-size masks retained by the closure until the cuts finish. Acceptable for `CUT_CONCURRENCY = 2`; do not raise it without checking the function memory size.

## What was checked
- Contract 2: `cutPieces` (`artworks.ts:288-306`) cuts `cutParts(original, [mask], clip)` per piece, stores public cleaned PNG, private alpha PNG and `previewCutPath`, then one `setCandidateCut`; queue is `pieces.slice(0, MAX_CANDIDATES)`; two workers (`CUT_CONCURRENCY`); a failing piece is logged and skipped. Hooks: `detectInBox` (so `framed` and `detect`; first candidate via `withOwnCut`, rest from `candidates.slice(1)` with the frame as clip, index-aligned with `placed`), `cutoutArtwork` (sorted `largestFirst`, aligned), plain photo path (all pieces; none is the row's own, correct as nothing is cut yet), single auto-select (`withOwnCut` only). First candidate is never re-cut. DTO exposes `cleanedUrl` only (and only when set).
- `setCandidateCut` (`queries.ts:210-216`): one UPDATE; the new jsonb is computed from the row's current `candidates` inside the same statement (order kept by `with ordinality`), and the WHERE `candidates @> [{id}]` makes it a no-op once the candidates were replaced. Atomic under read-committed (a concurrent writer makes the UPDATE re-evaluate against the newer row), so two concurrent cuts cannot lose each other's fields. Candidate ids are new UUIDs per `storeCandidates` call (`artworks.ts:~268`), so a replaced detection never shares an id with the new one: old candidates are not resurrected and a stale `cleanedUrl` cannot land on a same-id candidate whose mask changed. No other code path writes `candidates` while cuts run (the only writers are `createFromImage`, `detectInBox`, `cutoutArtwork`, `withOwnCut`, all before `cutPieces` is scheduled).
- Contract 3: `adoptReadyCut` (`artworks.ts:603-630`) applies for exactly one distinct id, no points, a ready candidate (all three fields), and either no box or `clipToBox` with the box clamped to exactly the whole picture (from `shapingTrace.imageSize` or the file); it writes `cleanedUrl`, `maskUrl`, `cutPathSvg`, `status: ready`, `lastError: null`, rebuilds products (`rebuildProducts` split out of `recut`, same failed/unpublished reporting), keeps the previous alt text, and runs `describe` in `runAfterResponse`; never calls `cutParts` or SAM. Not ready, points, or a smaller box fall through to the existing re-cut. It sits inside `cleanupArtwork`, so `select` (via `selectCandidate`) adopts too.
- `runAfterResponse` (`web/lib/pipeline/after.ts`): `after(task)` in a try; any throw (no request scope) runs `task` inline with await; `task` wraps `fn` in try/catch and logs, so neither path produces an unhandled rejection or a rejected promise. All routes that can schedule work (`artworks`, `detect`, `cutout`, `select`, `cleanup`) export `maxDuration = 300`, so the deferred work (about 10 s of cuts, or one describe) fits well inside the function's remaining time. Whether the request-scoped deadline signal (`lib/deadline.ts`) is inherited by the deferred task depends on Next's async-context handling; it is harmless either way (the timer is cleared on a normal answer, so the signal is never aborted).
- `docs/api.md`, ADR, progress, handoff, accessibility: wording matches the code, including that `detect` also starts background cuts, that `select` adopts, that the answer keeps the old description, that a late background cut for a replaced candidate is discarded, and that points or a smaller box re-cut. Gap: Major 2, Minor 3.
