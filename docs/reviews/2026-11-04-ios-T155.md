## Findings

### Minor 1 · An unsent pick survives Back (implementer's concern)
- **Where:** `ios/App/AppState.swift:420` (`pickedPieces`), `ios/App/Screens/Create/YourCutoutView.swift:490` (`pick`).
- **What:** The local pick lives on the flow, not on the screen. Tap piece 2, then Back: Change it (from "Fix the cutout") still shows piece 1's product, and reopening Your cutout shows piece 2 selected, with piece 2's cut on the stage. Use this then sends the pick.
- **Why it is acceptable for the submission:** Nothing is wrong on the server or in the saved state. Change it shows what was saved, and Back without Use this means "not saved", which is the contract ("the server hears only Use this"). When Your cutout is reopened, the stage and the strip agree with each other, and Use this does what the screen shows. A new crop (`setPhoto`) and `discardPhoto` clear the pick. The only oddity is that a choice the user walked away from is still there on return.
- **Suggested fix (optional, small):** Add `CreateFlow.forgetPick(for:)`, which sets `pickedPieces[id] = nil`, and call it in an `.onDisappear` of Your cutout when `.yourCutout(artworkId)` is no longer in the path (Back), so reopening shows the cut piece. Do not reset on a tab switch (the path is kept then). It is fine to leave this for after the submission.

### Minor 2 · Use this can drop a shown pick when the cut has no usable image size
- **Where:** `ios/App/AppState.swift:1007` (`Cut.pendingPick`) and `ios/App/Services/CutoutGeometry.swift:70` (`CutoutRequest.pick`), used from `ios/App/Screens/Create/YourCutoutView.swift:588`.
- **What:** `pendingPick` returns nil when `cut.box` and `cut.imageSize` are both unusable. `currentRequest` (`YourCutoutView.swift:164`) patches `imageSize` with `loadedSize`, but `pendingPick` does not. In that state a tap still selects piece 2 locally and shows its cut, and then Use this goes on without sending the pick, so piece 1 is saved while piece 2 was shown. Before T155, a tap in this state did nothing visible.
- **Why Minor:** The server and the mock always send `imageSize` with the candidates, and `loadPictureIfNeeded` fills `flow.photoImageSize` on the photo path, so this is very unlikely in practice.
- **Suggested fix:** In `useThis`, build the pick from the cut with the same `loadedSize` fallback that `currentRequest` uses (`var c = cut; if c.imageSize?.isUsable != true { c.imageSize = loadedSize }; c.pendingPick`). Or, in `pick(_:)`, refuse a local selection whose `pendingPick` would be nil.

### Minor 3 · "Your cutout is ready. Here it is." is shown under the spinner of a cut that is not ready
- **Where:** `ios/App/Screens/Create/YourCutoutView.swift:98` with `:337`.
- **What:** When the tapped piece has no `cleanedUrl`, the stage shows a `ProgressView`, but the visible line under it still says the cutout is ready. VoiceOver is not affected (nothing is announced, and the stage label is "Your cutout").
- **Why Minor:** This only happens in the fallback path (the server's background cuts are not ready yet), and it lasts at most 2 s plus one pick.
- **Suggested fix:** Show the line only when `cut.stageUrl != nil`.

### Minor 4 · `testANewPhotoForgetsThePick` does not test the new photo
- **Where:** `ios/Tests/LocalPickTests.swift:101`.
- **What:** The second assertion runs on `again`, a fresh `CreateFlow`, so it would pass without any reset code. Only `pickedPieces.isEmpty` after `discardPhoto` is really tested.
- **Suggested fix:** Call `recordPhoto` on the same `flow` after `discardPhoto` (or instead of it, to cover `setPhoto`), then assert that `flow.cut(for: "p1")?.selected == ["cand-1"]`.

## What was checked

- **Contract point 1 (2048):**
  - `CameraView.use` calls `ImageTools.normalized(image, maxPixels: 2048)`.
  - Every way in reaches it: the camera (`UIImagePickerController`), the library (`PhotosPicker` → `loadTransferable` → `use`) and the UI-test photo.
  - No other code normalises a creation photo. `ThankYouComposerView` already used the 2048 default.
- **`Candidate.cleanedUrl`:**
  - It is an optional `var` on a synthesised `Codable`, so a candidate without it decodes.
  - `testCandidateDecodesItsCut` covers both shapes.
- **A tap is local:**
  - `pieceChip` → `pick(_:)` → `flow.pickPiece` makes no request when the cut is present.
  - The stage reads `Cut.stageUrl` through `RemoteImage`, which reads `ImageCache.shared` synchronously with the same key as `ImageLoader.image(for:)` (`maxPixel` nil on both sides).
  - `preloadPieceCuts` (`.task(id: pieceCutURLs)`) loads every strip cut when the screen shows the strip, and runs again when a re-read brings new URLs. `ImageLoader` merges duplicate loads that are in flight.
  - A preloaded cut draws in the first frame, with no spinner.
- **Missing cut:**
  - `awaitPieceCut` sleeps 2 s, reads `GET /artworks/{id}` once and replaces the candidates.
  - It returns `pendingPick` only if the same piece is still selected, still pending and still without a cut. The fallback is sent with `announces: false`.
  - While it waits, `work = .pick` disables Use this, Apply cutout and the new-photo buttons and hides Back. This rules out a second tap meanwhile.
  - Unit tests cover the re-read that finds the cut, the fallback after one read, and another piece tapped meanwhile.
- **Use this:**
  - Marks that are not applied yet are sent first, with `candidateIds` = the selected piece, because `CutoutRequest.marks` reads the overlaid `cut.selected`.
  - Otherwise `cut?.pendingPick` is sent once, then the screen goes on as before.
