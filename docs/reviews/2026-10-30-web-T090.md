### Minor
1. **The number chips take taps from the drawing's top-left corner, also in box mode.** `web/components/create/screens/CutoutPhoto.tsx:106` and `web/components/create/Create.module.css:116` (`.chipHit`).
   - What: each chip's 44 px hit area starts at the piece's bbox top-left and sits above the tap layer. A pointerdown there never reaches the tap layer's `down`, so a box drag that starts at the drawing's corner draws nothing, and the click toggles the piece instead. On a small piece shown on a phone, the chip covers most of the piece, so an "Add area" tap on it toggles the piece instead of placing a mark.
   - Why: the creator's choice changes without warning while they think they are drawing a box. The live region does not report the toggle, because `toggle` speaks only when the change leaves the choice stuck.
   - Fix: give `chipHit` `pointer-events: none` while `mode === "box"`, or anchor the chip outside the bbox (above or left of it). Optionally, speak the toggle ("Piece 2 chosen / left out") in `toggle`.
2. **No test for the branch where moderation fails on edited text over a pending draft and nothing is persisted.** `web/lib/pipeline/products.ts:206`.
   - What: the new rule ("not written to either row") is in the code, decisions.md and api.md, but no test covers it. The existing moderation-failure tests have no `draftCopy`.
   - Why: this is the subtle branch of item 2. A regression would silently write a `moderation: {ok:false}` result for text that is neither the live copy nor the pending copy.
   - Fix: add one test in `test/approve.test.ts`: live listing plus a pending draft, `edits: { title: "bad" }`, `moderateResult = {ok:false}` → 409, then assert that neither `upsertListing` nor `setListingDraftCopy` ran and that `draftCopy` is unchanged.
3. **The Select screen's wiring has no component or browser test.** `web/components/create/screens/Select.tsx`, `Photo.tsx`, `CutoutPhoto.tsx`.
   - What: only the pure helpers are tested (`initialChoice`, `isStuck`, `boxRescueArtworkId`, `wholeImageBox`). Nothing exercises the relaxed `MissingState` gate (`candidates: []` must open the flow), the rescue button, the chip→`toggle` wiring, or the "no double announcement" claim. The report says so itself.
   - Why: these are the items most likely to regress silently. Lint and build do not catch an inverted condition.
   - Fix: before v0.6, run a `next dev` pass with a stubbed BFF (fixture `GET /artworks/{id}` with `candidates: []`, `cleanup` echo), or add one RTL test for `Select` with `candidates: []` that asserts box mode is checked, "Remove area" is absent and "Use the whole photo" sends `{box:[0,0,w,h]}`.
4. **`Tokens.Size.photoMaxHeight` is a fraction (0.65) inside a group of point values.** `ios/App/Theme/Tokens.swift:101`, `scripts/gen_tokens.ts` (the `vh` branch).
   - What: every other `Tokens.Size` member is in points. This one is a share of the screen height, and only a doc comment says so.
   - Why: a later iOS screen that writes `.frame(maxHeight: Tokens.Size.photoMaxHeight)` compiles and gives a 0.65 pt photo.
   - Fix: emit it under its own name or enum (`Tokens.Size.photoMaxHeightShare` or `Tokens.ScreenShare.photoMaxHeight`). The constant has no consumers yet, so this costs nothing now.
5. **The unpublished-product notice says the product can be published again, but not where.** `web/messages/en.json:421`.
   - What: "A bigger or clearer cutout lets you publish it again." On the web there is no page that republishes another product of this artwork (the handoff says so). Only the current product type continues to Ready.
   - Why: the creator gets an instruction they cannot carry out from this screen. This is mainly a problem when the unpublished product is the other type, for example an earlier tote.
   - Fix: add where to do it, e.g. "…publish it again from My designs in the app." (iOS has that screen), or "…publish it again after a new cutout."
6. **(nit) The web `ApiError.details` catch-all keeps every extra field and reuses the name `details`.** `web/components/create/api.ts:30`.
   - What: the server's error object can itself carry a nested `details` key (cleanup `details.failedProductIds`), so callers end up with `err.details.details`. Nothing leaks to the UI (`describeError` ignores it), but the field is wider than the brief's "carry the artwork id".
   - Fix: rename it to `extra` (or `fields`), or keep only known keys (`artworkId`, `artworkIds`, `details`).
