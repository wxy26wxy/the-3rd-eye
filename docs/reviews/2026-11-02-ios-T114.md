### Important
1. **The full UI suite is not green. `CutoutUITests.testDraggedBoxIsSent` fails every time** (`ios/UITests/CutoutUITests.swift:128`).
   - What: `box[0]` = 170.276 against 240 ± 48. The value was identical in the full run and in the isolated retry.
   - Why: the test now reaches Your cutout through a change (`openYourCutout`), so the photo is the remote original of `ch1`, not the local photo (`YourCutoutView.swift` `localPhoto`).
     - The mock serves a 1×1 PNG, and `RemoteImage` and its placeholder take their own aspect (`RemoteImage.swift:35`, `aspectRatio(1)`). So the `cutout-photo` element is not 3:4.
     - The app maps through `CutoutGeometry.fitRect` over that element, so it is consistent with itself. The test assumes the element equals the 1200×1600 picture, which held only for the local photo in the old `AdjustCutoutUITests`.
     - The y values fit this explanation: the image is fitted by height, so y maps exactly.
   - Failure scenario: the suite stays red for every run and for CI.
   - Fix (pick one):
     - Make the mock serve a 3:4 PNG for `originalUrl`, for example 3×4 px.
     - Compute the expected box from the element frame with fit-rect maths.
     - Reach Your cutout through the no-drawing path, which uses the local photo.
   - Real pictures should match `imageSize`, so the app's own behaviour is probably fine. Worth one manual drag on a real change result.
2. **Draft-product reuse can show a stale mockup and hides rebuild failures** (`ios/App/Screens/Create/MakingProductView.swift:35`; no unit test).
   - What: reuse keys only on `artworkId` + `type`. There are two ways to re-cut the same artwork id between the first Making your sticker and the second:
     - Listing details → Back → Your cutout → Fix the edges → Use this (`cleanup`).
     - Listing details → Back ×3 → Choose a pattern → pick another piece (`select`).
   - Why it matters:
     - The server rebuilds the product's print file and mockup on both routes (`web/lib/pipeline/artworks.ts` `selectCandidate` → `cleanupArtwork`; docs/api.md T080 §2). So reusing the product id is right.
     - But the client keeps the old `flow.product.mockupUrl`, and Listing details shows it (`ListingDetailsView.swift:56`). The creator sees the old cut while approving the new one.
     - A failed rebuild (`details.failedProductIds`) is stored in `flow.cutoutNotice` (`YourCutoutView.swift:507`), but only `DesignDetailView` reads it. In the Create flow it is silent. `select` drops `details` entirely.
   - Failure scenario: the creator fixes the edges after seeing the listing, taps Use this, and approves a listing whose preview is the old cut. The shop then shows the new cut (or, after a failed rebuild, the old print file with no warning).
   - Fix:
     - Reuse the product only when the cut has not changed. Record `artwork.cleanedUrl` on the product when it is made, and compare it before reusing.
     - When the cut has changed, refresh the product (re-read `GET /artworks` products for the mockup), and surface `cutoutNotice` on Listing details.
     - Add a unit test for both the reuse and the refresh paths.
3. **Your cutout's VoiceOver actions are probably unreachable, and absent when no drawing was found** (`ios/App/Screens/Create/YourCutoutView.swift:235-242`).
   - What:
     - "Box around your art" and "Add the area around your art" are attached to a view marked `.accessibilityElement(children: .contain)`. That is a container, not a focusable element.
     - The container's only children are the gesture layer, which is not an element, and any marks.
     - The actions also exist only `if let piece = selected.first`.
   - Why:
     - v0.7 put these actions on the piece buttons, which are real elements. The move to a container is unverified with VoiceOver.
     - In the "No drawing found" path, `resetCutout(… candidates: [])` leaves no selected piece, so there are no actions at all. "Use this" stays disabled (`canUse` needs a request), so a VoiceOver or Switch Control user can only tap Start over.
     - `docs/accessibility.md:49-50` still expects the pieces strip and "Leave this piece out", which no longer exist.
   - Failure scenario: a blind creator whose photo has no detected drawing cannot make a sticker at all.
   - Fix:
     - Make the photo a single element (`.accessibilityElement(children: .ignore)` with the label and actions, with marks exposed separately), or put the actions on an always-present element.
     - When there are no candidates, add an action such as "Use the whole photo" that sends a box over the full image.
     - Run one VoiceOver pass on a device, and update the accessibility script.
