## Findings

### Major
**M1. Tapping back to a marked piece shows its raw cut but "Use this" sends nothing (`web/components/create/flow.ts` `pickLocal` ~L240, `needsPick` ~L247).**
What: marks are applied on piece A (the row's cut is now A with marks, `cutFrom = A`, `points` set). The user taps B (local, `points` cleared), then taps A again. `pickLocal` shows A's candidate `cleanedUrl`, which is A's raw cut without the marks. `selectedIds[0] === cutFrom`, so `needsPick` is false and "Use this" sends no request. The row keeps the marked cut while the stage showed the raw one. The same happens on one tap: marks on A, then B, "Use this" is not reached; but A, B, A is enough.
Why: what the user sees is not what is saved; Change it and the product photo are made from the marked cut.
Fix: in `pickLocal`, when `cut.points.length > 0` (the row's cut carries marks) drop `cutFrom` from the returned state (`cutFrom: undefined`), so tapping away from a marked cut always makes the next "Use this" send the pick (which adopts the raw cut). Add a flow test: marks on c1, tap c2, tap c1, `needsPick` true.

### Minor
**m1. The YourCutout.tsx wiring has no test (`web/components/create/screens/YourCutout.tsx` `pick` L207-235, `goOn` L238-253).** The handlers read correctly: `pick` passes `cutout` to `pickPiece` and only shows the busy state when the cut is missing; `goOn` skips the send when `saved && (!needsPick || !box)`, else calls `save("use", pickRequest(...))` when saved, or the marks request (which carries `candidateIds: selectedIds`) when not. No wrong prop was found. Because M1 lives at the seam, add one screen test in `web/test/create-screens.test.ts`: render with two candidates carrying `cleanedUrl`, click piece 2, assert no `cleanup` call and the stage image `src` is piece 2's cut, click "Use this", assert exactly one `cleanup` with `candidateIds: ["c2"]`.

**m2. A tap still moves focus to the result (`YourCutout.tsx` L222-223, `focusOn("result")`).** This was right for a re-cut that took seconds. For an instant local tap it pulls focus off the strip, so a keyboard user must tab back to try the next piece. The tap also says nothing in the live region (the `aria-pressed` change is the only signal). Fix: for the local path skip `focusOn("result")` (keep focus on the pressed piece); optionally `say` a short existing string if one fits. Keep the focus move for the fallback (server) path.

**m3. The re-read does not persist the fresh candidates when it falls through to the pick (`flow.ts` `pickPiece`).** If the re-read returns candidates but not the tapped one, `fresh` is used only for `applyMarks`, which stores `{...fresh}`; that is fine. If the re-read fails (network), `cut` is used unchanged; also fine. No bug, but a re-read that returns the other pieces' cuts while the tapped one stays missing is stored only after the pick succeeds. Acceptable; noted for completeness.
