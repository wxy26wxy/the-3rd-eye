# API contract · `/api/v1`

Base: `${NEXT_PUBLIC_SITE_URL}/api/v1`. JSON in and out unless noted. Errors: `{ "error": { "code": string, "message": string } }` with 4xx/5xx.
Auth: `Authorization: Bearer <token>` from `POST /auth/code`. Dev-mode only (documented as non-production).
Media never goes through these routes except short audio (≤ 4 MB). Images/video go to Blob through the client-upload flow and are referenced by URL/pathname.

## Auth
`POST /auth/code` `{ code }` → `{ token, creator: Creator }`
`GET /creators/me` → `Creator` · `PUT /creators/me` `{ displayName?, studioName?, bioShort?, storyText?, accessPrefs?, mentionDisability? }` → `Creator`

## Uploads (Vercel Blob client upload)
`POST /uploads` body per `@vercel/blob/client` `handleUpload` protocol. Allowed: `image/*`, `video/mp4`, `video/quicktime`, `audio/*`. Pathnames: `creators/<creatorId>/<kind>/<uuid>.<ext>`. Response per protocol.

## Voice
`POST /transcribe` multipart `file` (m4a/mp3/wav, ≤ 60 s) or JSON `{ audioUrl }` → `{ text, language?, segments? }`

## Create
Since v0.8 the apps are photo-first. Since round 4 (T140–T143, v0.9.1) the order is: photo → Adjust the area **on the device** → the client uploads **only the crop** → `POST /artworks {source:"photo", imageUrl: <crop>, product, framed:true}` (detection on the whole crop, the largest piece cut) → Your cutout (`cleanup` with `points`, `box` = the whole crop) → **`products`** (made before Change it) → **`change`** → **`cutout`** → **`products`** (optional, repeatable) → listing. See "Creator flow (round 4)" for the exact calls per step (rounds 3 and 2b are kept below, superseded), and "Change it (T111)". `POST /prompts/shape`, `POST /artworks {source:"text2image"}` and `POST /artworks/{id}/refine` stay in the backend but are **not used by the apps since v0.8** (kept and tested; removal is a post-hackathon task).

`POST /prompts/shape` `{ transcript, answers?: string[], product: "sticker"|"tote" }` → `{ prompt, style_notes, clarifying_question: string|null, spoken_confirmation }`
`POST /artworks` one of:
- `{ source: "text2image", prompt, transcript?, product, n?: 1..4 }` → `{ artworks: ArtworkVariant[] }` (one row per variant; each has `altText`, `spokenDescription`, `differencesFromPrompt`, `genResponseId`)
- `{ source: "photo"|"canvas", imageUrl, product, detect?: boolean, framed?: boolean }` → `{ artwork: Artwork, candidates: Candidate[], imageSize: { w, h } }` (`framed: true` (T143, round 4): the picture is the creator's crop; detection as `detect {box: [0,0,w,h]}`, the largest piece cut, plus `details`; `detect: false` (T134): photo stored, `candidates: []`, no SAM, never 422; default `true`: SAM finds every drawing or object; `cleanedUrl` null until a candidate is chosen when `candidates.length > 1`; `imageSize` = pixel size of the stored original, the coordinate space of `bbox`, `points` and `box`)
`POST /artworks/{id}/select` `{ candidateId }` → `Artwork` (cleaned PNG + cut path)
`POST /artworks/{id}/detect` `{ box: [x0,y0,x1,y1] }` → `{ artwork: Artwork, candidates: Candidate[], imageSize: { w, h }, details }` (SAM inside the frame, largest cut out and clipped; T134)
`POST /artworks/{id}/refine` `{ instruction }` → `{ artwork: ArtworkVariant }` (new row, `parentArtworkId` set) (not used by the apps since v0.8)
`POST /artworks/{id}/change` `{ instruction, transcript?, clientRequestId? }` → 201 `{ artwork: ArtworkVariant, description: { alt, spoken, differences } }` (new child row; T111)
`POST /artworks/{id}/cutout` → `{ artwork: Artwork, candidates: Candidate[], imageSize: { w, h }, details, products: ArtworkProduct[] }` (SAM on the artwork's picture, largest piece cut out; T111; `products` T143)
`POST /artworks/{id}/cleanup` `{ candidateIds?: string[], points?: { x, y, label: "positive"|"negative" }[], box?: [x0,y0,x1,y1], clipToBox?: boolean }` (at least one of the first three) → `Artwork & { details, products: ArtworkProduct[] }` (see T080 clarifications; `clipToBox` since T126; `products` T143)
`GET /artworks` → `{ artworks: ArtworkListItem[] }` (mine, newest first; each carries `products` with `priceCents`, `title`, `description`, `mockupUrl`, `previewUrl`)
`GET /artworks/{id}` → `{ artwork: Artwork, candidates: Candidate[], imageSize: { w, h } | null, originalUrl: string | null }` (`originalUrl` presigned, valid 10 min)
`DELETE /artworks/{id}` → `{ id, deleted: true, archivedProductIds: string[] }`

## Products and listings
`POST /products` `{ artworkId, type: "sticker"|"tote", clientRequestId? }` → `Product` (sticker: `printPngUrl`, `printSvgUrl`, `mockupUrl`, `previewUrl`; tote: `mockupUrl`, `previewUrl: null`) — may take up to 60 s
`POST /listings/{productId}/run` → `{ listing: ListingDraft, trace: AgentStep[] }`
`GET /listings/{productId}` → `{ product: Product, listing: Listing | null, draft: ListingDraft | null }` (T134)
`POST /listings/{productId}/approve` `{ approvedVia: "voice"|"tap", edits?: { title?, description?, priceCents? }, acceptPrintWarning?: boolean }` → `{ product: Product, listing: Listing, storyVideoNeeded: boolean }`

## Story video (per creator, once)

`GET /creators/me/story-prompts` → `{ prompts: string[3] }`

## Orders, thank-yous, messages

`GET /orders/{id}` → `{ order: Order, thankYou: ThankYou|null, messages: Message[] }`
`POST /orders/{id}/thank-you` `{ text?, imageUrl?, videoUrl?, transcript?, draft?: boolean }` → `draft` → `{ draftText, provider }` else `ThankYou`
`GET /orders/{id}/messages` → `{ messages }` · `POST /orders/{id}/messages` `{ body }` → `Message`
`POST /story/draft` `{ transcript, mentionDisability }` → `{ headline, bio_short, story_text, provider }`

## Public (web, no auth; server actions on the pages, listed for completeness)

## Clarifications (T010 backend, 2026-10-28)
Additive only; no existing field or path changed.
1. **Media access (`GET /media/{pathname}`).** Public, no auth: a creator's current story video, and these path kinds: `creators/<id>/{mockups|cleaned|thumbs|avatar|story-video}/...` (mockups, cleaned art and thumbs are also returned as direct public Blob URLs). `?tag=<nfc token>` (alias `?t=`): only that order's thank-you video and image (never print files, originals or masks). Creator auth (Bearer or `ms_creator` cookie): the creator's own files. Admin basic auth: everything (print PNG, die-cut SVG). Private originals, masks and print files live in the private Blob store. The route answers `302` to a short-lived URL (range requests work for video).
2. **Uploads.** Client uploads (`POST /uploads`) land in the public Blob store under `creators/<creatorId>/<kind>/<uuid>.<ext>`. Use kind `story-video` for story videos, `thank-you` for thank-you media, `photo` / `canvas` for artwork sources, `audio` for recordings. The token request needs creator auth (Bearer or cookie). After `POST /artworks` (photo/canvas) stores the private original, the server deletes the public upload only when its kind is `photo`, `photos` or `canvas` (T090); any other own file sent as `imageUrl` is read but never deleted.
3. **Audio format.** Muse Voice Transcribe accepts **WAV only** (verified live: `audioEncoding: "WAV"` is the only accepted value; m4a/mp3/webm/ogg are rejected). `POST /transcribe` accepts any format, passes WAV through, and converts others with ffmpeg when the server has it (local dev). **Vercel has no ffmpeg, so in production send WAV** (16-bit PCM, mono, 16 kHz is ideal): web decodes the MediaRecorder blob with `AudioContext.decodeAudioData` and encodes WAV; iOS records Linear PCM WAV. Non-WAV without ffmpeg → `415 unsupported_audio`.
4. **Captions for videos.** `POST /creators/me/story-video` and `POST /orders/{id}/thank-you` accept an optional `audioUrl` (Blob pathname of a WAV of the video's soundtrack); captions are made from it. Without it the server tries the video itself (works only where ffmpeg exists); when captioning fails the video is still saved and `storyVideoVtt` stays null. Cue times are estimated (the API returns no timestamps) by spreading the measured duration over sentence-sized cues.
5. **`cutPathSvg`** is an SVG path in a `0 0 100 100` viewBox: the cleaned PNG fitted `contain` and centered in that square. The white border extends a few units past 0–100; render with `overflow: visible`. A cut of several separate pieces has one `M…Z` subpath per piece; draw the whole `d` (T108). Pieces less than about 6.5 mm apart in print (measured: a gap of about 78 px at 300 dpi, 2.2 × the 3 mm border) share one outline; otherwise the two cut lines stay at least 2 mm apart (the cut mask is closed by 1 mm so no sliver under 1 mm is left to tear). The preview uses the same border in the cleaned PNG's pixels, so it shows the same number of pieces as the print. Pixel-exact die lines are in the private print SVG, with the same rule.
6. **`Creator.split`** (`{ creator_bps, org_bps, production_bps }`) is included in `/auth/code`, `GET/PUT /creators/me` and `/creators/me/story-video`. Creator share of a price = `floor(price * creator_bps / 10000)`.
7. **Public actions over HTTP** (same as the lib functions in `web/lib/pipeline/public.ts`, for clients that prefer fetch): `POST /public/orders { productId, buyerName, buyerEmail?, shipNote? } → { orderId, token }`; `POST /public/tap { token } → { tapCount }`; `POST /public/reply { token, body } → Message`.
8. **Sign-in cookie.** `POST /auth/code` also sets the httpOnly `ms_creator` cookie; every creator route accepts it in place of the Bearer header.
9. **Client-supplied file references** (`imageUrl`, `videoUrl`, `audioUrl` on `/artworks`, `/transcribe`, `/creators/me/story-video`, `/orders/{id}/thank-you`) must be the caller's own uploads: a pathname `creators/<yourId>/<kind>/<file>` or an `https://<public-store>.public.blob.vercel-storage.com/creators/<yourId>/...` URL. Anything else → `403 forbidden_path | forbidden_url`. `/transcribe { audioUrl }` is capped at 4 MB (`413 too_large`).
10. **Errors may carry extra fields** inside `error`, e.g. `{ "error": { "code": "deadline_exceeded", "message": "...", "artworkId": "...", "artworkIds": [...] } }`.
    - Long routes (`/artworks*`, `/products`, `/listings/*`) answer within 270 s: on timeout `504 deadline_exceeded` with the artwork id(s) created so far; those rows stay `status: "draft"` with `lastError` set (new nullable `Artwork.lastError`). Other pipeline failures also set `lastError` and include `artworkId`.
    - `POST /artworks` photo/canvas with no drawing found → `422 no_drawing_found` (with `artworkId` and a hint in `message`).
    - `POST /listings/{id}/approve` → `409 print_check_failed` when the print check failed, `409 moderation_failed` when the text fails moderation. Edited title/description are moderated again before publishing, so edits cannot bypass the check; `409 listing_missing` before the agent ran. A missing `edits.priceCents` keeps a **published** product's live price (the agent's suggestion only prices a draft); a missing `title`/`description` keeps the live listing text when the request has any `edits`, even if a pending re-run draft exists; in that case the saved row's tags, print check and agent trace also come from the live listing, the print-check gate and moderation use the live row (with its tags), and the pending draft is discarded (T090). An approve with no `edits` publishes the pending draft whole (text, tags, print check, moderation, trace). Omit `priceCents` to keep the price: `priceCents: 0` is not empty (it is clamped to 100).
11. **`product` on `POST /artworks`** is used: text prompts get the product's print style appended when they were not shaped for it; it is recorded on the artwork (`shapingTrace.product`).

## Clarifications (T050 fix wave, 2026-10-29)
Additive; no existing field or path removed.
1. **Video captions need `audioUrl` on Vercel.** `POST /creators/me/story-video` and `POST /orders/{id}/thank-you` caption from `audioUrl` when present (a WAV of the video's soundtrack, uploaded with kind `audio`: `creators/<id>/audio/<uuid>.wav`, 16-bit PCM mono 16 kHz, ≤ 10 MB, about 3 minutes). Without it the server tries the video itself, which works only where ffmpeg exists (local dev). When captioning fails, or the soundtrack is silent, the new video is saved with `storyVideoVtt: null` (thank-you `videoVtt: null`): old captions are never kept for a new video.
   - **Web:** the story-video screen decodes the picked video's audio with `AudioContext.decodeAudioData`, downmixes and resamples to 16 kHz (`lib/audio/wav.ts#blobToWav`), uploads the WAV and sends `audioUrl`. If the browser cannot decode the audio, the video is sent without it.
   - **iOS:** reads the recorded movie's audio track with `AVAssetReader` (output settings: Linear PCM, 16-bit little-endian integer, 1 channel, 16 000 Hz), writes a WAV header around the samples, uploads it as kind `audio` and sends its pathname as `audioUrl` with the video (story video and thank-you video).
2. **Story draft from the video (`Creator.storyDraft`).** After a story video is captioned, the server drafts a story from the transcript (`draftStory`, Muse Glimmer locally, Spark fallback) and stores it on the creator. `GET /creators/me`, `PUT /creators/me` and `POST /creators/me/story-video` return `storyDraft: { headline, bio_short, story_text, provider, mentionDisability, createdAt } | null`. Nothing is published until the creator accepts it with `PUT /creators/me { storyText, bioShort? }` (that also clears `storyDraft`). `POST /story/draft { transcript?, mentionDisability }` drafts from `transcript`, or from the stored video transcript when `transcript` is omitted, stores it as `storyDraft` and returns it. `provider` is `ollama` (Muse Glimmer on the development Mac) or `meta-fallback` (Muse Spark 1.3, always on Vercel).
3. **Talking points** (`GET /creators/me/story-prompts`) use the creator's most recently chosen artwork: the newest `ready` artwork that has a product.
4. **Creator tokens expire.** Tokens are `<creatorId>.<expiresAtUnixSeconds>.<signature>`, valid 30 days, checked on every request (`401 unauthorized` when expired or malformed). `POST /auth/code` issues a fresh token. Older tokens without an expiry are rejected; sign in again.
5. **Login codes** are random 10-character codes generated by the seed (letters and digits without look-alikes). They are not in the repository; see `web/.creator-codes.local` (git-ignored) on the machine that ran the seed.
6. **Upload limits** (`POST /uploads`): images 25 MB, video 200 MB, audio 10 MB (by the pathname kind: `audio` → audio types, `story-video`/`thank-you` video files → video types, otherwise images). SVG is not accepted. A malformed JSON body answers `400 invalid_json`.
7. **Buyer notes are moderated.** `POST /public/reply` and the story-tag form reject unkind or unsafe notes with `422 note_rejected`; ship notes on `POST /public/orders` likewise (`422 note_rejected`, the order is not placed). When the moderation provider itself fails, both answer `503 moderation_unavailable` (never 500) and nothing is stored: the reply's message says to try again in a minute; the order's says to remove the note and try again (the order does not need it) (T090).
8. **Listing agent results are the server's.** `print_ok` = the resolution check and the contrast check, computed by the server (the tools are run server-side when the model skipped them); moderation runs on the final title and description. `ListingDraft.print_ok` and `notes` reflect those results, not the model's claim. Re-running `POST /listings/{id}/run` on a published product does not touch the live listing: the new copy is kept as a pending draft (`listings.draft_copy`) and goes live only through `approve` (which re-checks print and moderation and clears the draft).
9. **Tote print file.** `POST /products` with `type: "tote"` now returns `printPngUrl` (private, 150 dpi, short side ≥ 1500 px, transparent background kept); `printSvgUrl` stays null for totes.
10. **Orders store the production share** (`orders.production_share_cents`), computed with the creator and organization shares at order time.

## Studio-issued creator codes (T070, 2026-10-29)
Additive; no new public route and no change to `POST /auth/code`.
1. **Where codes come from.** The studio (admin, basic auth) adds a creator on `/admin` → Creators → Add creator, or makes a new code for an existing one. Both are Server Functions behind the admin auth check, not public API. There is no self-sign-up. A new code is a random 10-character code (`web/lib/codes.ts`, same alphabet as the seed); it is shown once on `/admin` and never listed again.
2. **Sign-in link.** Two forms, both only pre-fill the code field (trimmed, uppercased, ≤ 64 characters); the person still taps Sign in, which posts the code as before. Treat both like a password.
   - **`/create/code#c=<CODE>`** (T090): the link the admin card shows and copies. The code is in the fragment, which browsers never send, so it is not in request logs or link-preview fetches; the page reads it with JavaScript and then removes it from the address bar. Without JavaScript the field stays empty (type the code).
   - **`/create/code?c=<CODE>`**: only inside the admin card's QR code, because some scanner apps drop the `#` part. This request reaches the server and its logs; the QR is for showing in person. The page also removes `c` from the address bar after load. The iOS form of the same link is `the3rdeye://code/<CODE>`; the app registers the scheme and pre-fills its code screen the same way.
3. **Rotating a code** (`/admin` → New code) makes the old code and its link fail with `401 invalid_code`. Tokens already issued (`<id>.<exp>.<sig>`) are not tied to the code and stay valid until they expire (30 days).
4. **Hidden creators** (`creators.hidden`, for testing): left out of shop grids, `/artists`, the featured artist, "more from this studio", and `/c/<slug>` (not found). A direct product link `/p/<id>` still opens and can be bought, `/t/<token>` keeps working for their orders, and they can sign in and use every creator route.

## Clarifications (T080 backend, 2026-10-29): adjust the cut-out, manage designs
Additive except `cleanup`, whose body changed (no client called it before; `phrase` is gone).

1. **Coordinates.** `Candidate.bbox`, cleanup `points` and `box` are pixels of the **stored original**: origin top-left, x to the right, y down, size `imageSize { w, h }` (returned by `POST /artworks` for photo/canvas and by `GET /artworks/{id}`). It is not the size of the photo the client uploaded (the server rotates it by EXIF and may upscale it up to ×2). A box is half-open `[x0, y0, x1, y1)` with `x0 < x1`, `y0 < y1`. Negative values are rejected (`400`); values past `w`/`h` are clamped to the image. Convert a tap on a view showing the original (aspect-fit) as `x = (tapX - imageLeft) * imageSize.w / shownWidth`, same for y; non-integers are fine (the server floors).
2. **`POST /artworks/{id}/cleanup`** body `{ candidateIds?, points?, box? }`, at least one key (`400 invalid_request` otherwise):
   - `candidateIds`: 1–6 ids from this artwork's `candidates` (`400 invalid_candidate` for any other id). The cut-out is the **union** of those candidates; no model call, a few seconds. One id behaves like `select`. Use it for "combine pieces".
   - `points`: 1–10 `{ x, y, label }`. `label` is `"positive"` (part of the object) or `"negative"` (not part of it); it defaults to `"positive"` when omitted. Negative-only points need `candidateIds` or a `box` (`400 invalid_request` otherwise).
   - `box`: the whole object (`[x0, y0, x1, y1]`, see 1).
   - **Always send the current selection with the adjustment:** the client keeps the chosen `candidateIds` and sends them together with every `points` / `box` edit. The labels apply to the **combined result**:
     - a **negative** point removes the whole connected piece of a chosen candidate that it lands on (no model call; e.g. a shadow that SAM returned as a separate piece, or one of two combined pieces);
     - a **box** or any **positive** point adds one SAM object, prompted with the box and all points (negative points also shape that object), unioned with the candidates.
     - Not supported: carving part of a single connected candidate piece away with a negative point (it removes the whole piece). Use a box around what should stay, plus negative points, instead.
   - **`clipToBox`** (boolean, default `false`; T126): the box also **limits** the cut. After the union above (candidates, minus negative pieces, plus the SAM object), every pixel outside the box is cleared, then the mask is finished and the cut trimmed as usual, and the finished soft edge is cleared outside the box too, so nothing of the cut lies past the frame. The box is clamped to the image and covers every pixel it touches (start floored, end rounded up). A frame smaller than the piece therefore trims it; a frame larger than the piece still only adds. `clipToBox: true` without `box` → `400 invalid_request`; a box that leaves nothing → `422 no_drawing_found` (nothing is stored). Without the flag (or `false`) the box only adds, exactly as before. **The "Adjust the area" screens (web and iOS) send `{ candidateIds: [piece], box, clipToBox: true }`**; the other edge tools do not send it. The mock (`ios/scripts/mock_api.py`) applies the same validation and echoes the body, `clipToBox` included, in `GET /__mock/last/cleanup`.
   - The mask is finished on the server (holes filled, small gaps closed, specks dropped only when under 0.5 % of their piece **and** under 0.02 % of the frame / 64 px, soft anti-aliased edge) before the cut.
   - Response: `Artwork` with a new `cleanedUrl` (a new URL every time, safe to cache), `cutPathSvg`, `altText`, `spokenDescription`, `status: "ready"`, plus `details: { failedProductIds: string[], unpublishedProductIds: string[] }`. When nothing is found, or the selection is too small to cut → `422 no_drawing_found`.
   - When the artwork already has products, their print files and mockups are rebuilt from the new cut-out in the same request, in parallel (one mockup image call each, about 16 s; the whole request still answers within 270 s or `504 deadline_exceeded`). The new cut-out is kept even when a rebuild fails: those products keep their previous files and are listed in `details.failedProductIds` (call cleanup again with the same body to retry). Each rebuilt product's print check (resolution, contrast) is recomputed; a **published** product whose check now fails is moved back to `draft` (`details.unpublishedProductIds`) and must be approved again. Product ids, price and listing text do not change; a published product's shop image changes with the new cut.
   - `maskUrl` (private) after a cleanup is the soft mask at the cut's working size (the original upscaled by the same factor as `cleanedUrl`, at most ×2), not necessarily the original's size.
3. **`GET /artworks/{id}`** (own artwork, else `404 not_found`) → `{ artwork: Artwork, candidates: Candidate[], imageSize: ImageSize | null, originalUrl: string | null }`. `originalUrl` is a presigned URL of the stored original (valid 10 minutes, fetch it directly; do not store it); `imageSize` is its size. Both are null only for rows without an original. Use it for "Re-do the cutout" (show the original, draw the box / points, call `cleanup`) and to resume an artwork whose candidate was never chosen.
4. **`GET /artworks`** items carry `products: ArtworkProduct[]` (newest first; empty when none) for status badges. `priceCents` is the product's live price; `title` and `description` are the saved listing text (null before the listing agent ran); `mockupUrl` is the public mockup (null before it exists). Clients prefill the edit form from these.
5. **Tile state** (both clients): `status: "ready"` and `cleanedUrl` set → show the cut-out; `cleanedUrl` null and `lastError` set → failed (offer "Re-do the cutout" or delete); `cleanedUrl` null, no `lastError`, `candidates.length > 1` in `GET /artworks/{id}` → waiting for a choice (open the picker). A tile never needs an endless spinner.
6. **`DELETE /artworks/{id}`** (own artwork, else `404 not_found`) → `{ id, deleted: true, archivedProductIds }`. Soft delete: the artwork leaves `GET /artworks` and `GET /artworks/{id}` answers 404. Its products are set to `status: "archived"` and leave the shop (shop list and product page). Orders already placed keep working: `GET /orders`, `GET /orders/{id}` and the story-tag page `/t/{token}` still render. Not undoable through the API.
7. **Candidates for photos of objects.** A photo now looks for both drawings and physical objects (two SAM phrases, overlapping results merged, anything covering more than 95 % of the frame dropped, a result covering more than 40 % of the frame whose box contains a higher-scoring result dropped as the paper or table, at most 6). `Candidate` is unchanged. A single candidate is auto-selected only when it covers at most 50 % of the frame and no surrounding paper/table result was dropped; otherwise `cleanedUrl` stays null and the client shows the picker with that one candidate.

### Print check (ruling 2: a warning, never a block, except resolution)
- **Resolution** (the only hard gate): measured on the artwork's **cleaned PNG** (not the print file) allowing **one further ×2**: OK when `min(w, h) × 2 ≥ 900 px` (sticker, 3 in at 300 dpi) / `1500 px` (tote). Note: the cleaned PNG may itself already be up to ×2 of the photo's pixels (the cut is upscaled when small), so in the worst case the print is about ×4 of the photo's pixels; a stricter rule is a one-line change.
- **Contrast** (a warning): measured in Lab over the **opaque pixels only** (alpha ≥ 128): lightness spread `L p95 − p5 ≥ 30` **or** colourfulness `chroma p90 ≥ 25` **or** a dark piece (mean `L ≤ 50`). Faint pencil on white and evenly toned light-grey pieces warn; yellow, pastel, colourful and dark pieces pass.
- `ListingDraft.print_ok` = **true only when neither check is flagged**; `ListingDraft.print_check` = `"resolution"` (failed; reported first when both are flagged), `"contrast"` (warning only), or `null`. The listing form shows the line for `print_check`.
- `POST /listings/{id}/approve`:
  - resolution failed → `409 {error: {code: "print_check_failed", message, check: "resolution"}}`, **even with** `acceptPrintWarning: true`. Client: "Re-do the cutout" / "Use a bigger photo".
  - contrast warning and no `acceptPrintWarning` → `409 {error: {code: "print_check_failed", message, check: "contrast"}}`. Client: "Use anyway" → the same approve with `acceptPrintWarning: true` → 200 published.
  - A listing saved under the old rule (before v0.9) is measured again under these rules at approve time (and saved), so drafts that failed the old greyscale rule can be published.
- After a re-cut (`cleanup` / `detect` with products), a **published** product goes back to draft only when **resolution** fails (`details.unpublishedProductIds`); a contrast warning leaves it published.

- First call → 201 as before. A repeat with the same id → **200 with the same row** (no new row; no new image edit or product build once the first call has stored its row); for `change` the `description` is rebuilt from the row (`alt`, `spoken`, `differences`), and when the row has none yet (the first call is still describing it, or its describe failed) it is described for the repeat. If that also fails, `alt` / `spoken` are `""`: clients always fall back to their own copy when they are empty.

**Superseded and failed crop rows (T146).** Rows 1 and 2 leave rows behind: a re-frame in the same session makes a new row, and a frame that answers `422 no_drawing_found` leaves an empty draft row. Clients delete them with [`DELETE /artworks/{id}`](#clarifications-t010-backend-2026-10-28) (soft delete, archives the row's products): the superseded photo row **after** the new `POST /artworks` succeeds (a failed new upload keeps the old row), and a 422 row on the next "Use this area" (frame changed or not) or on "Take a new photo". A failed delete is logged and ignored. A row that has a published product is never deleted. The web does this in `components/create/flow.ts` (`dropRow`).

`POST /artworks {detect: false}` and `POST /artworks/{id}/detect {box}` are **not used by the apps since v0.9.1**, kept for the round 3 TestFlight build (both keep working). The plain `POST /artworks {source:"photo"}` (no `framed`, no `detect`) keeps its whole-photo behaviour for the round 2b build in the field: it drops a paper/table-like result, auto-cuts only a single small piece and leaves `cleanedUrl` null when there are several (not what a tight crop needs, hence `framed`).

### `framed` on `POST /artworks` (T143)
- `framed?: boolean` (default `false`); with `source: "photo"|"canvas"` only. `framed: true` with `detect: false` → `400 invalid_request`.
- Stores the picture like `detect: false` (same EXIF rotation, flatten, ×2 cap; one stored original), then runs the `detect` pipeline with the box `[0, 0, w, h]`: SAM on the whole picture, candidates largest first, the largest cut out and clipped to the picture.
- → **201** `{ artwork /* cleanedUrl, cutPathSvg, status "ready" */, candidates, imageSize, details: { failedProductIds: [], unpublishedProductIds: [] } }`.
- Errors: `422 no_drawing_found` with `artworkId` (the row exists, `lastError` set, `candidates: []`; a later `detect` or `cleanup` on it still works), `504 deadline_exceeded`, plus the plain `POST /artworks` errors. Time ≈ 10–25 s (two SAM phrases in parallel + describe). Rate-limited as a model route.

### `products` on `cleanup` and `cutout` (T143)
- `POST /artworks/{id}/cleanup` → `{ ...Artwork, details, products: ArtworkProduct[] }`; `POST /artworks/{id}/cutout` → `{ artwork, candidates, imageSize, details: { failedProductIds, unpublishedProductIds }, products: ArtworkProduct[] }` (`details` as on `cleanup`).
- `products` = the row's **live** products (not deleted, not archived), newest first, read **after** the rebuild: `{ id, type, status, priceCents, title, description, mockupUrl, previewUrl }` (the `ArtworkProduct` shape of `GET /artworks`; `title` / `description` from the listing, null before the agent ran). `status` may have turned `draft` (see `details.unpublishedProductIds`). Empty when the row has no product yet.
- `GET /artworks` items' `products` already carry `mockupUrl` and `previewUrl` (since T087 / T121; archived products are listed there too, with `status: "archived"`).

### `POST /products` on a change result
Works like any row once its `cutout` ran (`status: "ready"`, `cleanedUrl` set): the product is built from the change result's cut. Before its `cutout` → `409 artwork_not_ready`.

### Caching (T143, ruling 3)
- Public pictures (`mockupUrl`, `previewUrl`, thumbs, `cleanedUrl`) are written once to new pathnames and never overwritten, so Blob serves them with `cache-control: public, max-age=31536000` (one year): cache them by URL.
- `GET /media/<pathname>` answers its 302 to the presigned URL with `Cache-Control: private, max-age=540` and `Vary: Authorization, Cookie` (just under the 600 s presign); the streamed fallback (no presign possible) stays `private, no-store`, and refusals (401/403/404) carry no cache lifetime.

**Mock (`ios/scripts/mock_api.py`).** `POST /artworks {framed: true}` behaves like `detect` on p1 in one call (`MOCK_DELAY_MS`, 4 s with `SLOW…`; `ONE…`: one candidate; `NONE…`/`NOCUT…`: `422 no_drawing_found` with `artworkId: "p1"`; with `detect: false` → 400); photo `POST /artworks` calls in `/__mock/count/artworks-posts` (after the 400 check), `GET /artworks` calls in `/__mock/count/artworks`. `cleanup` (p1, d<n>, ch<n>) and `cutout` answer with `products` for the row (rebuilt: each `mockupUrl` gets a new `&v=` so a swap is visible). `POST /products` takes `ch<n>` rows (`404` unknown, `409 artwork_not_ready` before its `cutout`; product id `pr-ch<n>-<type>`; p1 and d<n> keep `pr-new-<type>`), and counts per row at `/__mock/count/products/<artworkId>` next to the total `/__mock/count/products` (repeats with the same `clientRequestId` are not counted). `GET /artworks` change rows list their products; every product there carries `mockupUrl` and `previewUrl` (null when the mock has none).

**Mock delays and sessions (T145).** Every artificial delay of the mock is set by the environment variable `MOCK_DELAY_MS` (default `150`): the framed photo, `detect`, `change`, the listing `run` and text2image answer after it (they slept 2 s before; `MOCK_DELAY_MS=2000 python3 ios/scripts/mock_api.py` brings that pace back for a demo). The in-flight windows a UI test needs are fixed and apply only in their sign-in modes: `SLOW…` 4 s (framed photo, `cleanup`, `products`), `LOSTCHANGE…` 4 s (the change, then the dropped answer, counted at `/__mock/count/change-dropped`), a code holding `SLOWRUN` 2 s (the listing run, so the drafting card shows), `NONE…` / `NOCUT…` 2 s (the framed photo's 422: a faster 422 lands while Making your cutout is still sliding in and the advice on Adjust the area is lost, an app race found in T145). The UI tests start the mock with no variable. Parallel UI test runners share one mock through sessions: a sign-in code ending in `-S<digits>` opens that session (its own modes, counts, last bodies, designs and changes) and answers the token `c-test.mock.<digits>`, which keeps the app's later calls in it; the path prefix `/s/<digits>/` does the same for the runner's `/__mock/...` reads and the app's blob PUTs (`MOCK_BLOB_API`). Calls with neither use the default session, as before.
