## Behaviour checked against a running build (`next start`, curl with `x-forwarded-for`)
- `POST /api/v1/artworks` (and `?x=1`, `/api/v1/prompts/shape`): 20 × 401, then 429. Correct.
- `/api/v1/%61rtworks`, `/api/v1/Artworks`: 404, so no bypass on the direct API. `//api/v1/...` and a trailing `/` get a 308 first.
- `POST /t/<token>` (server-action shape): 31st call → 429, `retry-after: 60`, `cache-control: no-store`, JSON envelope.
- **BFF:** with a dummy `ms_creator` cookie, 20 calls to `/create/bff/%61rtworks` from IP A went through, then 429. After that, the **first** call to `/create/bff/artworks` from a different IP B also got 429, and every call after it did too. See Critical 1.

## Strengths
- The limits live in one place (`lib/rate-limit.ts:15`). Classification is POST-only, uses anchored regexes, and rejects `artworksx`.
- A blocked request is not recorded, so a blocked client does not push its own lockout further out. Each key's array holds at most `limit` entries (`lib/rate-limit.ts:51-57`). `Retry-After` is computed from the oldest hit in the window, which is correct for a sliding log.
- The map is bounded: stale keys are evicted, then the least recent keys go once it passes 10,000. Re-inserting a key on every allowed hit keeps the Map in recency order.
- The 429 body matches the existing `{ error: { code, message } }` envelope, and the create flow's `describeError` shows the message (4xx path in `components/create/errors.tsx`). The create flow does not crash.
- The docs are candid that the limit is per instance and not global.

## Issues

### Critical
1. **BFF traffic shares one bucket keyed on the server's own IP. One web creator can lock out every other web creator, and normal use double-counts.** `app/create/bff/[...path]/route.ts:18-27` forwards to `/api/v1/<path>` with `fetch()`. That inner request goes through `proxy.ts` again because the matcher now includes `/api/v1/:path*` (`proxy.ts:37`). `forwardHeaders` (`components/create/forward.ts:9-20`) does not carry the client IP, so the inner hop is keyed on the forwarding server's address:
   - locally that is loopback;
   - on Vercel it is the function's egress IP. Vercel also rewrites `x-forwarded-for` at its edge, so forwarding the header would not help there.

   Result: all web creators share one `model:<server-ip>` bucket of 20 POSTs per minute per instance. Reproduced above: IP B was 429'd on its first call after IP A used up the quota. One artwork in the web flow costs several model POSTs (transcribe, shape, artworks, cleanup, products, listing run), so two or three judges using the web flow at once will hit 429. Each user's calls are also counted twice: once on their own IP at the BFF hop, once on the shared key.

   Fix: key the `model` group on the bearer token (a hash of `Authorization`; every model route requires it and the BFF attaches it), falling back to IP when the header is absent. Then either skip limiting at the `/create/bff/` hop (the inner hop sees the canonical path and the token), or mark the inner hop with a server-secret header and skip it there. Either way, add a proxy test that walks the BFF → inner path, or at least asserts that two different tokens behind the same IP do not share a bucket.

### Important
2. **The BFF hop is classified on the raw, still-encoded pathname, so it can be bypassed.** `lib/rate-limit.ts:18-20` tests `req.nextUrl.pathname`, but the catch-all `params.path` is decoded before forwarding (`route.ts:16-18`). `/create/bff/%61rtworks` is therefore not limited at the BFF hop and still reaches `/api/v1/artworks`. Today the shared inner bucket (Critical 1) hides this. Any fix that exempts or re-keys the inner hop exposes it. Limit on the decoded path (`decodeURIComponent` per segment), or limit only at the inner hop as suggested in 1.
3. **The docs claim the Playwright and mock flows turn the limiter off, but nothing does.** `docs/architecture.md:33` and `docs/handoffs/backend.md:64` say so. No Playwright config, script or `.env` in the repo sets `RATE_LIMIT_DISABLED`, and the iOS `ios/scripts/mock_api.py` does not go through the proxy at all. Either wire the env var into the flows that hammer these routes or reword the docs to "set it when…". Combined with Critical 1 this matters locally: every BFF model call also counts against the shared loopback bucket.

### Minor
4. **`RATE_LIMIT_DISABLED=1` is honoured in production** (`lib/rate-limit.ts:87`), with no `NODE_ENV`/`VERCEL_ENV` guard. The docs present it as a local switch. If it is set on Vercel by mistake, it silently removes the mitigation. Guard it with `VERCEL_ENV !== "production"` or say explicitly in architecture.md that it works in prod.
5. **Proxy globals.** `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md:19` says proxy "should not attempt relying on shared modules or globals". Proxy runs on Node by default (same file, l.255), and Fluid Compute does reuse instances, so per-instance state works in practice. The docs should still say the counters can reset whenever an instance is recycled, not only that they are counted per instance (`lib/rate-limit.ts:1-7`, `docs/architecture.md:33`).
6. **The proxy now runs on more requests.** The matcher grew to all of `/api/v1/:path*` and `/t/:path*` (`proxy.ts:37`), so every iOS GET, every buyer view of a story tag page and every upload now invokes the proxy, only for `classify` to return null. A matcher cannot filter by method, but it can list only the limited paths: `/api/v1/auth/code`, `/api/v1/public/:path*`, `/api/v1/(artworks|products|listings|prompts|transcribe|story)/:path*`, `/t/:path*`. That reduces the extra invocations on Hobby.
7. **The sign-in form shows raw JSON on 429.** `components/create/screens/CodeSignIn.tsx:20` and `components/create/SignOut.tsx:11` are native `<form method="post" action="/create/code/session">`. On 429 the browser renders the JSON body as a page. Sign-out POSTs also count toward the 10/min auth bucket for that IP. For `/create/code/session`, a 303 to `/create/code?error=rate_limited` would be kinder; sign-out could be excluded (intent is in the form body, so it may be easier to leave it).
8. **The note form has no error boundary on 429.** `sendReply` is a server action POSTed to `/t/<token>`. A 429 JSON reply is not an RSC payload, so the action rejects inside `useActionState`, and `app/t/[token]` has no `error.tsx`. The likely result is the default client error page. `tap` uses `void onTap(...)` (`components/storytag/TapOnce.tsx:11`), so it only produces an unhandled rejection. Tap and note share one 30/min bucket per IP; buyers on one venue wifi share it too.
9. **IPv6 is keyed per full address** (`lib/rate-limit.ts:32-36,95`). One client with a /64 can rotate through addresses and bypass the limit. Bucketing IPv6 by /64 is a cheap fix. Off Vercel (local or self-hosted), `x-forwarded-for` is client-controlled. The code is right to trust it on Vercel, where the edge overwrites it and `x-real-ip` carries the same value, but the docs do not say the IP is trusted only behind Vercel.
10. **Eviction under a flood of fresh keys scans the whole map on every new key** (`lib/rate-limit.ts:58,64`). At the cap with no stale entries, each new key costs one full 10k scan plus one delete. That is bounded and cheap enough, but it is O(n) per request on the hot path during the exact attack it is meant to absorb. Optional: skip the stale pass when the oldest key (Map head) is still fresh.
11. **Tests.**
    - They pass `now` explicitly instead of using fake timers. That is fine for the limiter, but the proxy tests run on real `Date.now()`, so nothing checks that the proxy resets after the window.
    - There is no proxy-level test for `/create/code/session`, `/t/*`, the BFF path, or that GETs pass through.
    - The cap test (`test/rate-limit.test.ts:30-38`) does not check that the most recent key survives eviction.

## Declined to judge
- Exact Vercel behaviour for the inner hop: which egress IP appears, and whether Vercel routes an internal same-deployment fetch through the edge and the proxy. I reproduced this on `next start` only. The shared-bucket outcome holds whatever the inner IP is, since it is not the client's.
- Whether Vercel deploys the Node proxy as its own function or co-locates it with the routes, and therefore how often instances (and so counters) are recycled.
- Whether the limit numbers (10/30/20) fit real demo usage. They are as briefed.

## Assessment
Ready to merge: No. Critical 1 breaks the mobile-web creator flow as soon as more than one person uses it. Merge after Critical 1 and Important 2–3 are fixed; the Minors can be parked.

### Verdict on the original findings
- **Critical 1: resolved.** The BFF hop counts on the real client IP (`components/create/forward.ts:18`). The inner hop skips only when the signature verifies (`lib/rate-limit.ts:131-132`).
- **Important 2: resolved.** `classify` decodes each path segment (`lib/rate-limit.ts:31-34`). Decoding can only make a path match more groups, never fewer.
- **Important 3: resolved.** The docs now say the variable is set by hand and that the iOS mock API never goes through the proxy. Also applied: Minor 4 (`VERCEL_ENV=production` ignores the variable, `lib/rate-limit.ts:128`), Minor 5 and 9 docs notes, Minor 6 (matcher narrowed), Minor 9 (IPv6 keyed by /64).
- **HMAC compare:** constant time (`timingSafeEqual` after an equal-length check). Lengths are fixed for hex SHA-256, so the length check leaks nothing useful.

### New or remaining
- **Important (new): no domain separation from the creator-token HMAC.** `lib/rate-limit.ts:59-62` computes `HMAC-SHA256(CREATOR_SESSION_SECRET, ip)`. `lib/auth.ts:31,42` signs creator tokens as `HMAC-SHA256(CREATOR_SESSION_SECRET, "<creatorId>.<exp>")`, and only the output encoding differs (hex vs base64url, which convert into each other). The signed value comes from `x-forwarded-for`. Off Vercel that header is client-controlled, so any leak of a BFF signature, for example a future debug log of request headers on the inner hop, is a creator-token forgery oracle. It does not leak today (checked above). It is a one-line fix: sign `"t3e-bff-ip:" + ip`, or derive a subkey such as `HMAC(secret, "rate-limit")`.
- **Minor (new):** the signature is bound only to the IP. It carries no path, method or timestamp, so a leaked pair would let anyone skip the inner limiter on every route, from any IP, until the secret rotates. Fine for now; bind a minute timestamp if it is cheap.
- **Minor (new):** `docs/handoffs/backend.md:62` still says "`proxy.ts` now also matches `/api/v1/*`". The matcher is now the narrowed list.
- **Minor (new):** no test for the missing-secret path. With the secret unset, `bffIpHeaders` should return `{}` and the inner hop should count on the connection IP. Verified by hand above.
- **Tests requested:** all three are covered: two IPs through the BFF, the encoded path, and a forged signature (`test/rate-limit.test.ts:86-111`).
- **Still deferred, as stated in the report:** Minors 7, 8, 10, 11.
- **Regressions:** none found. The narrowed matcher still covers `/admin`, `/create` (including the BFF), and every limited `/api/v1` and `/t` path.

### Assessment
Ready to merge: With fixes. Add domain separation to the BFF HMAC first; the rest can be parked.
