## Issues
### Critical — none.
### Important
1. **"Re-do the cutout" after a resolution refusal opens Your cutout, not Adjust the area** (`ListingDetailsView.swift` `redo()` in the `refusal` branch → `app.backToCutout()`, `AppState.swift:202-212`). Web parity ruling broken; the creator cannot enlarge the frame. Fix: `backToArea()` — cut `createPath` back to `.adjustArea` when present; for a design from My designs open `AdjustAreaView(origin: .designs)` via `GET /artworks/{id}`; keep Redo-while-drafting → Your cutout; unit test + NORES UI assertion.
2. **Recovering a product can pick the wrong one** (`CreateFlow.recoveredProduct` under `reconcile`): first non-archived product of that artwork + type, no request-id or "new since the job started" check (`ArtworkProduct` carries neither). Scenario: Design detail → Make another sticker (one published, no draft) → transport error → reconcile returns the published sticker → run/approve rewrite the live listing. Fix: record known product ids at job start and accept only a new id (prefer drafts), or re-POST with the same `clientRequestId` (server dedupes); test with an existing published product.
3. **Recovering a listing accepts any existing draft** (`reconcile` `.listing`): returns `GET /listings/{id}`'s `draft` whenever the title is non-empty; `recoverRun()` cancels the live run and shows it. Scenario: "Improve with AI" with an earlier draft, background a few seconds, return → the old draft is applied, the new run cancelled. Fix: remember the draft title/updatedAt at job start and require a change, or skip `.active` recovery while the request is in flight (reconcile only after a transport error).
4. **Recovering a change can pick an earlier attempt's child** (`CreateFlow.recoveredChange`): the fallback "same parent + instruction, created after start − 120 s, newest" includes children with a different `clientRequestId`. Scenario: same instruction twice within 2 min after Back to my original → ch1 applied, the real answer dropped by `finishJob`. Fix: exclude children whose `clientRequestId` is non-nil and different; extend `testRecoveredChangeIsTheChildMadeAfterTheJobStarted`. (Checked fine: newest wins on ties; ISO dates with/without fractions; nothing on the server → Try again reuses the id.)
5. **`detect` can be sent twice after a tab switch** (`MakingCutoutView` `.task(id: attempt)` guarded only by `@State running`, false again once the call finishes; the task re-runs when the view is still mounted on the Create tab's return before `replaceTop` lands) → the flaky UI failure; also `recordDetect` runs `resetChange()` twice. Fix: return at the top of the task when `app.createPath.last != .makingCutout(job)` or the flow already has the cut for this box / change id.
### Minor
- The background UI test does not exercise recovery (`testChangeSurvivesTheAppGoingToTheBackground`): the background task lets `change` finish. Fix: `ch<n>` rows in the mock's `GET /artworks` + a SLOW-change mode, kill the request, assert recovery with a change count of 1.
- Blank picture card under Increase Contrast (`surfaceAlt == surface`, no border): add a thin `colors.border` stroke in high contrast.
- Stale `pendingJob` survives navigation; clear it on `resetChange()` / a new photo.
- Two drafting tests only check presence (`.exists`); acceptable because the Redo test asserts behaviour.
