## What was checked
- Fix 1, route: the previous pathname is read with `getCreatorById` before the captioning and the update; the delete is after `updateCreator` and guarded by `previous && previous !== pathname`; a failure goes to `console.warn` through `.catch`, so the request still answers 200. If `updateCreator` throws, the delete is never reached. The route test pins the order `read, update, delete`, the no-previous and same-pathname skips, and warn-and-200.
- Fix 1, script: `previousVideo` is read after `findCreator` and before `putVideo`. The dry run returns before any of this (the test asserts no `previous` read and no delete). The delete runs after the `update` row check, so a failed update never deletes (test). A delete failure is `deps.warn` and the run continues (test). The log line "removed previous video" prints a pathname only.
- Public-store copy case: `lib/storage/blob.ts` `delete` calls `deleteRaw`, which loops over `candidates(path)`. With private credentials the candidates are the private store at the pathname, then the public store at the plain pathname; without them, the hashed public pathname, then the plain public one. Each `del` tolerates `BlobNotFoundError`, so a blob that lives only in the public store (June's current video, stored there by the one-off script under the `story-video` kind) is deleted by the second candidate, and a miss in the other store does not throw. Other errors still throw, and the callers turn them into a warning.
- Fix 2: the 302 carries `private, max-age=540` only when `isPublicKind(pathname)`; otherwise `private, no-store`. `Vary: Authorization, Cookie` is unchanged. `PUBLIC_KINDS` in `lib/media-access.ts` includes `story-video`, so creator and tag pages keep the cached redirect for the story video. Which requests are allowed is unchanged: the access logic above the redirect was not touched in the diff. A public-kind file is still readable by anyone, as before; the only change is a shorter cache lifetime for non-public files. A creator's own original and tag-authorised thank-you media are `no-store`; the legacy "current story video through the database check" case (non-public path) is also `no-store`, which is the safe side. The streamed fallback keeps `no-store`. The changed T143 test is justified: it used an admin request on a print file, which is now correctly `no-store`; it was rewritten to use a public mockup (cached) and the new test covers tag and admin as `no-store`.
- Fix 3: `createFromImage` waits `DELETE_RETRY_MS` (250 ms) only inside the `.catch` after a first failure, so the normal path is not slowed. A second failure goes to the existing warning. The test pins first-throws-second-succeeds with no warning, and both-throw with exactly one warning and no throw. The wait uses real timers (about 250 ms per failing case), acceptable.
