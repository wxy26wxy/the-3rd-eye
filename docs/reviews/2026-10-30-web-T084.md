## Strengths
- The request body matches the contract. `makeRequest` (components/create/cutout.ts:70-79) always sends the chosen `candidateIds` with `points`/`box`. It refuses a body with only negative points and no ids or box, caps ids at 6 and points at 10, and uses the exact `"positive"`/`"negative"` labels. `chooseAction` sends `select` only for one piece with no marks.
- The coordinate mapping is right for the actual CSS. `.cutPhoto` (Create.module.css:107) is 100% wide with the image's aspect ratio, so it is only letterboxed when `max-height` clamps it, and then only left and right. `.cutStage` (:108) is centred horizontally at full height, which is exactly what `fitRect` computes from the `.cutPhoto` rect. The border is on `.cutFrame`, outside the measured box, so it does not shift taps. `fitRect`/`imagePoint`/`imageBox` are tested in both letterbox directions, including the offset and clamping.
- The 422 advice only replaces the error when negatives were sent (Select.tsx:29-34). It reuses the brief's exact Remove-area copy, and the same copy refuses a mark that would leave nothing (Select.tsx:105).
- Apply works as an honest commit. It writes `cutoutNotice` into the draft, "Use this" skips a second call when the request is unchanged (Select.tsx:88, 161), and any edit made after Apply sends a new request.
- Accessibility basics are covered:
  - Native checkboxes and a native radio group, so arrow keys work.
  - Real per-piece buttons, labelled by the piece.
  - Marks are 44 px buttons with names.
  - Selected state is shown by fill plus a ✓ (list) and a solid outline plus ✓ (photo), not by colour alone.
  - The tap layer is hidden from assistive tech.
- All CSS tokens resolve in app/tokens.css or globals.css, and every string is in en.json. The notice copy matches the brief word for word.
- Photo.tsx now routes to Select whenever there is no cut and at least one candidate (T080 §7). This fixes a latent bug where a product could be made from an uncut artwork.

## Issues

### Critical
None.

### Important
1. **Navigation is not locked while a request runs, and a late `router.push` can pull the user back.** Select.tsx:185 (`back={retake}`) and :194 (Retake `href`) stay live during `apply`. During `use` the footer disappears, but the header Back link is still live. If the creator taps Back or Retake mid-request:
   - `goOn` still runs `router.push("/create/ready")` (:172) when it resolves, dragging them away from the photo screen.
   - `apply` still writes `update({ cutoutNotice })` (:144) into the draft. If Photo.tsx has already reset `cutoutNotice` for a new photo, a stale product notice from the old artwork shows on the next Ready.

   iOS disables Back and Retake and cancels or guards navigation (ios.md T082, "While a request runs…").

   Fix: hide or disable Back and Retake while `busy`. Before `router.push` and `update`, check a mounted/`artworkId` ref, for example a `live` ref set false on unmount.
2. **Focus is not managed after Apply or Use.** The Apply button disables itself while running (:191). On success the photo, the mode radios and the per-mode instruction unmount (:202-233), and nothing receives focus. Browsers then drop focus to `<body>`, so a keyboard or screen-reader user starts again from the top of the page. The status text "Your cutout is saved" is announced, but the user is lost. The same happens on "Use this", where the whole footer is removed (:188).

   The brief explicitly asks for focus management after Apply.

   Fix: after a successful apply, focus the "Back to photo / Show the cutout" toggle (:215) or the checker image region with `tabIndex={-1}`. On error, focus the ErrorNotice.
3. **The 10-minute presigned `originalUrl` has no recovery path.** The `<img>` at CutoutPhoto.tsx:64 has no `onError`. The detail is fetched once per mount (Select.tsx:74-80; `once` only de-dupes requests in flight, so a remount does refetch, but nothing in the screen triggers one). There is a realistic path on this screen:
   1. The creator stays more than 10 minutes and taps Apply.
   2. They tap "Back to photo".
   3. CutoutPhoto remounts the `<img>` with the expired URL. Unless the browser cached it, it renders as an empty frame with no message. Taps still map, but the creator is marking blind.

   Fix: on `onError`, refetch `GET artworks/{id}` once (keyed so it is not de-duped onto the stale result) and swap `originalUrl`. If that fails, show `t.photoMissing`.

### Minor
1. **Notices may not be announced** (Select.tsx:236). The refusal, max-marks and product notices are rendered by mounting a new `<Status role="status">` that already contains its text. Several screen readers (notably VoiceOver on Safari) do not announce a live region that is inserted with its content. The refusal path also does not call `say()`. Fix: also pass these through `say()`, or keep one permanent live region.
2. **Apply and "Use this" disable silently** (Select.tsx:190-191). With no piece checked and only Remove marks, `makeRequest` returns null and both buttons go disabled with no explanation. `leavesNothing` returns false when nothing is selected, so the mark is accepted without warning. Fix: show `t.instructionRemove` or a "Pick a piece" line when `request` is null and there are marks.
3. **A retry after a failed "Use this" re-sends cleanup** (Select.tsx:161-176). If cleanup succeeds and `makeProduct` then fails, Retry calls cleanup again, which rebuilds products and costs time. Fix: after the in-`goOn` cleanup succeeds, `setApplied({ request: action.body, artwork: art })` so the retry skips it.
4. **The applied artwork is not kept in the draft** (Select.tsx:141-144). iOS sets `flow.artwork` on Apply. The web keeps it only in component state, so a reload after Apply shows piece 1 checked, and "Use this" then calls `select`, overwriting the saved combined cut without a word. This is acceptable for the hackathon. Store `{request, cleanedUrl}` in the draft if cheap.
5. **The unpublished notice points to "My designs", which does not exist on the web** (messages/en.json:411). On the web the path is rare: Select runs before `makeProduct`, so products only exist if the creator goes Ready → browser back → Select, and only a *published* one can be unpublished. The brief also says "same strings". Keep it for now, but log a follow-up for a web variant, for example "…Approve it again before it goes back in the shop."
6. **The Remove-mark refusal is approximate** (cutout.ts:94-106). `leavesNothing` tests whether the point falls in the candidate's bbox. The server removes the connected mask piece the point lands on. A mark in empty space inside the bbox is refused although the server would keep the piece. A candidate made of several connected parts is treated as gone after one mark. This is a bounded false refusal and the 422 path covers the opposite case. Note it in the handoff.
7. **Tests do not cover the screen's own rules** (test/cutout.test.ts). Only the pure helpers are tested. Untested: `cleanupError` (422 maps to the advice only with negatives; otherwise `describeError`), the "Use this after Apply makes no call" rule, and `locate()`, which is where the border-offset bug was found in the browser. Fix: export `cleanupError` and add 2–3 cases. Optionally, add a small render test of Select with a mocked `api`.
8. **Raw values in CSS.** `.mode input { width: 1px; height: 1px }` (Create.module.css:156), `opacity: 0.6` (:159, :171) and `65vh` (:107, :141). `1px` copies the existing `.pick input` pattern (:75). Prefer the global `.visually-hidden` utility, a disabled-opacity token if one exists, and a `--size-photo-max` token.
9. **Parity gaps in the deviations.** I judged both acceptable for now:
   - Photo chips are not tappable (iOS chips toggle). The checkbox list gives the same control with a single accessible path, and iOS also hides the chips from VoiceOver. Log it as a follow-up.
   - No zero-pieces box path. This is pre-existing behaviour: the web shows Retake on the `POST /artworks` 422 because `ApiError` drops `artworkId`. It needs an `ApiError` change, so it is out of scope for T084. Log it.
   - No My designs page on the web, so no delete or continue. This is correct per the brief ("do not invent a new page").
