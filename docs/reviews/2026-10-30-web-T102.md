### Important
1. **Forced-colors (high contrast) shows every choice as selected.** `web/components/ui/ChoiceCard.module.css:75` (`.check { color: transparent }`) and `:79`.
   - What: the check glyph is hidden only by `color: transparent`. In forced-colors mode the browser replaces `color` with CanvasText and drops backgrounds, so every card draws a check. The selected fill and border colour are lost as well.
   - Verified: chrome-devtools `forcedColors: active` on `/create/product`, with Sticker checked and Tote not. Both cards show a black ring with a check, and both `.check` colours compute to `rgb(0,0,0)`. Screenshot: `/private/tmp/claude-501/-Users-yao-Documents-Meta-Global-AI-Developer-Hackathon/73aeaf07-c28a-4464-8b11-0bd5f7dba4a7/scratchpad/t102-review/390-create-product-forced-colors.png`.
   - Why it matters: `/accessibility` promises "the site follows your device's high-contrast setting". The base showed no selection in this mode; this change actively shows the wrong state on product cards and method rows.
   - Failure scenario: a low-vision creator using Windows High Contrast picks Tote, sees both cards ticked, and cannot tell what Next will submit.
   - Fix:
     - Hide the glyph structurally, not by colour: for example `.check svg { visibility: hidden }` plus `.card:has(.input:checked) .check svg { visibility: visible }`.
     - Add `@media (forced-colors: active) { .card:has(.input:checked) { border-color: Highlight; outline: var(--focus-width) solid Highlight; } .card:has(.input:checked) .check { background: Highlight; color: HighlightText; } }`.
2. **Text inputs lost their visible boundary.** `web/components/ui/Field.module.css:9` and `:11`.
   - What: the control changed from a `surface-alt` fill with a 1.5 px border to a white fill with a 1 px `#D1D5DB` border. That is about 1.5:1 against the white card and page, below the 3:1 that WCAG 1.4.11 asks for input boundaries.
   - Not covered by the existing flag: `docs/accessibility.md:79` flags `#D1D5DB` only for unselected cards (found by their radio) and secondary pills (found by their text). An empty input has neither.
   - Visible on `/p/<id>` "Buy this piece" (name, email, note) and `/t/<token>` "Send a note". Screenshots: `t102-review/1440-product.png` and `390-storytag-full.png`.
   - Failure scenario: a low-vision buyer cannot find where to type their name on checkout.
   - Fix: keep a fill on the control (`--surface-alt`, as before), or give inputs a 3:1 border such as `--text-muted` (4.8:1). Then add the input row to the Designer flags table.

### Minor
1. `web/components/site/CreatorCard.module.css:15`: `.name` still uses the old display treatment (`font-weight: 400; text-transform: uppercase; line-height: 1`). On `/artists`, "JUNE PARK" renders in regular caps, a leftover from the old display font. It also carries a raw weight. This file is not in the diff, but it is a visible old-brand remnant on a visited route. A one-line fix: titleL weight, no uppercase. It could also go to T106.
2. `web/components/ui/Mascot.tsx:21`: `loading` defaults to `lazy`, and `CreateScreen.tsx:30` and the shop hero do not pass `eager`. The Welcome and hero mascots are above the fold and likely the LCP element; lazy defers them. Default to eager, or pass `eager` from `CreateScreen` and the hero.
3. `listening → front` still renders `mascot-front.png` (204 px source) at 84 CSS px on `/accessibility` (`StaticPage`). At 2x DPR it looks visibly posterised (`t102-review/390-accessibility.png`). The decision says it looks bad "above about 100 px", which does not cover 2x screens. Map `listening` to `book` too, or cap the size, until a better source exists.
4. `web/messages/en.json:499-501`: `mascot.listening`, `mascot.cheering`, `mascot.waving` are now unused because Tag goes through Mascot's `book|front|magnifier`. Dead keys; delete them or note them for T106.
5. No unit tests were added for the new or changed primitives (Mascot alt from en.json, LogoMark decorative/labelled, StepPill visually hidden, Scallop/Starburst render null). The suite count is unchanged.
6. Focus-ring colour is inconsistent: the global ring is ink (`--text`), but `CreatorCard.module.css:13`, `ProductCard.module.css:15` and `Create.module.css:82,98,147,171,190` still use `--focus-ring` (`#1E3A24`) at 1.5 px. Both pass contrast, but the decision says one ring "on every interactive element". Align them in the per-screen tasks or here.
7. History hygiene (as the report says): b8ada56 alone does not build. HEAD builds.
